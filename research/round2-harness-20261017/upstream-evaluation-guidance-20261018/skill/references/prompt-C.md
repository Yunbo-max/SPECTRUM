# C — 条件下的真实失效与不必要依赖

诊断失效前按[官方实现优先](prompt-upstream-code.md)核对并按需复现相关上游行为，区分模型局限、条件变化和本地适配/评分伪影。旧项目代码产生的低分本身不能证明研究 gap。

目的：在具体、值得研究的环境、约束或任务条件下，找出现有强方法的真实局限，或某条可以放宽的计算/信息依赖。不要预设原方法一定失败；边界可以是成本、延迟、质量、鲁棒性、信息保存或更新能力。

从核心论文和官方代码出发，结合 B 的知识提出数学解释和可证伪预测。选择能区分解释的现有 benchmark、模型、数据和 evaluation，写代码并实际运行。可以从一个有辨识力的模型/数据集开始，但不能用随意玩具例子替代相关任务，不能因为已有缓存就默认选择小模型。

把观察与原因分开。适当使用干预、反事实和简单强对照，判断缺陷是否来自实现错误、评分适配、信息差、预算差、调参不足、截断、随机波动或任务地板/天花板。对照设计由具体解释决定，不要求每次调试或单独评分同时运行所有方法。先测原输出、先诊断一个方法都是合理动作。

C 应形成足够清楚的问题：在哪些条件下发生、频率和后果如何、什么机制可能解释、什么结果会否定它。它是可修改的研究判断，不是冻结的问题合同。自然分布和人为改变条件都可研究，但应说明条件的现实意义，避免专为削弱某个基线而挑设置。

结果支持就进入 D；不支持就修改解释、实验或问题，必要时回 B。负结果写回记忆。无需 B02/B03/B04 拆成小 worker、Natural Gate、PASS 文件或固定输出格式。
