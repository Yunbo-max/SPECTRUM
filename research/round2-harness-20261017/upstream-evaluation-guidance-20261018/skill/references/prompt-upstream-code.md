# 官方实现优先：评测与代码疑点

B/C/D/E 中使用已有方法、benchmark 或评测代码，以及对已有代码、结果或实现结论产生疑问时，先查对应论文作者、模型作者或 benchmark 维护者发布或明确推荐的代码、文档和设置。项目旧代码、缓存配置和社区实现都需要核对；小红书等讨论是寻找线索的入口，不能替代上游依据。已有记忆包含适用且可追溯的源码版本时可直接复用，不必每次重新搜索。

按疑点阅读和必要时运行官方实现，核对相关的数据版本与划分、任务集合、prompt/chat template、生成参数与截断、答案提取/清洗、测试执行、超时和指标计算。记录来源与实际 commit/tag、关键设置和本地修改即可，不要求固定表格或报告格式。官方数据、模型作者采用的第三方 evaluator、作者自己的 evaluator 应分别说明，不能把“使用官方数据的自写评分器”称为官方评测。

优先直接使用适用的上游 evaluator 和原生指标。允许在授权 GPU 上自主安装、适配硬件/依赖、调 batch/并发并 debug；检查这些修改是否影响科学含义。不要悄悄重写提取或评分语义来让结果通过。如果疑似上游有 bug，定位问题并做针对性复现，保留上游原行为与修复差异；官方实现也可以被证据推翻。

官方实现不存在、不可访问或与研究条件不兼容时，明确证据缺口和替代来源，采用有依据的最小适配继续诊断。未经核对的结果标为诊断性结果，不能据此断言模型失效、基线弱或新方法优越。涉及评分或协议变化时，保留旧输出和结果版本；只在输入、任务集合和协议确实兼容时复用生成结果，否则重新生成，不混合不同协议的数字。

C 用这些检查区分真实失效与实现/评测伪影；D 的局部机制实验沿用可比较的上游评测；E 扩大验证时说明继承和修改的设置。证据不足就回 B 补来源或重设计实验。以上是研究判断和 debug 指导，不增加 Harness 数据库准入、审批、强制输出 schema 或每个命令的执行门槛。
