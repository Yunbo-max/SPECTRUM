# D — 数学机制与可执行的新方法

局部实验也遵循[官方实现优先](prompt-upstream-code.md)：从相关上游实现构造方法，在可比较的原生评测下检验机制；出现异常时先核对源码与协议，再决定修改方法或评测。

根据 C 的条件、失效或不必要依赖构造方法。说明原结构的哪条条件可以放宽，利用了什么数学/数据规律，新信息流、状态更新或计算组织为何有效，以及它会引入什么新问题。区分有条件推导、直觉和需要实测的预测，不要求每个想法都有完整定理。

把数学对象落到真实代码和可测量行为：它改变哪个算子、状态、目标或决策；哪些干预能验证机制；什么结果会说明机制错误。复用相关论文代码，允许在实际 GPU 上改实现、安装依赖和 debug，实验反馈也可以迫使公式与方法重写。

用现有相关模型、数据、benchmark 和 evaluation 做真正的局部实验。范围可以比 E 小，但应足以判断机制，而不是只证明代码能跑。优先有解释力的对照，如不干预、固定/随机策略、传统门控或更简单的优化；按问题选择，不强制全套清单。排除额外信息、更多计算和偶然误差带来的假优势。

D 与 C/B 持续循环：新的方法可能暴露 C 的诊断错误，新的论文可能使创新失去意义。及时修改或放弃，不因投入成本坚持旧方法。记录支持、反例、稳定性和仍未知的范围。

当局部实验证据支持机制、可复现且主要替代解释已被认真检查，直接进入 E 扩大验证。这里的 verified 是对证据的科学判断，不是必须由某个独立进程签字的状态或阻止执行的合同。
