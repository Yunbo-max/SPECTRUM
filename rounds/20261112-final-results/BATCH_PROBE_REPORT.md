## 2. Probe method

One probe run = one native `improving run --config … --resume` on a fresh output dir,
with a minimal config derived from the real case protocol:

- `rounds: 1`, single method `plain` (calibration is not a batch-dependent stage and is
  skipped for plain; a spectral case's calibration peak is recorded separately).
- `data_limits`: 2 training tasks → `train_samples=1` → exactly **2 optimizer steps**
  at `train.batch_size=1, gradient_accumulation_steps=1`; 1 eval task; 2 calibration tasks.
- The base-evaluation stage calls `generate_to_file` with the candidate generation triple;
  the post-training evaluation repeats it on the 2-step student. `record_stage` resets
  `torch.cuda.max_memory_allocated` per stage, so `evaluation.resources.json` and
  `post_training_evaluation.resources.json` hold the probe peak (`max_rank_allocated_bytes`
  for the single rank = `cuda_peak_allocated_bytes`, device 0).
- `evaluation.backend: none` (no code execution), no transfer-gap/operator-probe diagnostics.
- Each run writes `probe_result.json` (all stages, peaks, elapsed, tokens/s, SFT stats).
- Triples are reported as `(batch_size, task_batch_size, sequence_batch_size)`; the
  effective generate() batch is
  `min(batch_size, samples_per_task) * min(task_batch_size, sequence_batch_size // min(batch_size, samples_per_task))`.

Real protocol geometry per group: raw MBPP prompts average 37 tokens (max 72); the
chat-rendered prompts used by generation average ~66 tokens. Prompts therefore do not
dominate padding; the generation peak is KV cache plus decode/prefill and sampling
workspaces. MBPP completion lengths are ~180 tokens for Qwen7B historically and ~258
tokens for Qwen1.5B in the smoke run (fully capped at 512 for ~9% of samples).

Probe config core (generated by `make_probe_config.py`, one file per run):

```json
{

  "data_limits": {"train": 2, "calibration": 2, "validation": 1, "eval": <ceil(S/B)>},
```

## 3. Measurements

Memory model used to bracket candidates: the generation peak is
`weights + fixed runtime buffers (~3.5–4.5 GiB) + S × (KV bytes/token × actual
prompt+completion tokens + one-layer MLP prefill workspace)`. MBPP completions
average ~260 tokens for the 1.5B model (23/256 hit the 512 cap in the smoke run).
KV per token (bf16): Qwen1.5B 28 KiB, Qwen3B 36 KiB, Qwen7B 56 KiB,
deepseek-6.7B **512 KiB** (32-layer full MHA). Deepseek additionally carries a
~14.5 GiB reserved-vs-allocated gap at S=160 (allocator/transient), which is why its
safe S is much lower than the KV-only estimate. Its clean low-S fit is
allocated = 12.61 + 0.318·S GiB, reserved = 12.6 + 0.369·S GiB (S=96/128).

How to apply a triple:

- **train cases** (`kind=train`): put the triple in `config.generation.batch_size /
  task_batch_size / sequence_batch_size`. Leave `train.batch_size=1` and
  `gradient_accumulation_steps=16` unchanged (effective batch 16 is part of the frozen
  protocol; see §6.4). The same triple drives train synthesis (16 samples/task) and
  evaluation (64 samples/task).
- **transfer cases** (c16/c17): pass the third number as `--sequence-batch-size` to
  `experiments/iclr2027/transfer.py`; that script sets all three knobs to the same value.
- **decoder/interpolate cases** (c20-c22, c46, c32-c35): `scripts/rebuttal_decoder_eval.py`
  and `scripts/rebuttal_interpolation_eval.py` currently hard-code `(1,1,1)`; they need a
  small patch to accept the triple before the table can be applied.
- Plans freeze `config_sha256` / `implementation_sha256` / `plan_fingerprint`, so any
  change must be made **before** planning, in a fresh run root.
- Use the **same triple for every compared arm** in a group: batching changes the
  `batch_seed` RNG stream (`generation.py`), so mixing triples across arms would also
  change the sampled completions.

## 5. Failures / OOM brackets

- `q7b-gen-s896-b16` (base 71.95 / 78.39 GiB; post 63.73 / 69.81 GiB),
  `q7b-gen-s1024-b16` (base 71.04 / 78.43 GiB; post 78.09 / 78.44 GiB) — **rejected**:
  the base stage exceeds the safety line even though the S=896 post stage is fine.
  The base spike is a real risk for the first evaluation of every run.
- `q7b-gen-s800-b16` — base 66.51 / **76.42 GiB** reserved: below 76.9 but above the
  ≈72 GiB safety target. Recorded as an over-line bracket; S=768 is the 7B choice.
- `ds-gen-s208-b16`, `ds-gen-s224-b16`, `ds-gen-s256-b16` — **OOM brackets for
  deepseek-6.7B**: all hit the device wall (`CUDA out of memory`, exit code 2;
  e.g. 78.16 GiB in use of 79.18 GiB). S=208/224/256 are rejected.
- `ds-gen-s192-b16` (73.70 / 78.50 GiB) and `ds-gen-s160-b16` (63.51 / 78.04 GiB)
  completed, but their **reserved** peaks are above the 76.9 GB safety line. They are
  recorded as over-line brackets; the deepseek recommendation is S=144 (S=128 fallback).

No other probe failed. `q7b-gen-s768-b16` completed safely and is the 7B
recommendation. `q7b-gen-s800-b16` was still finishing its post stage; its base
stage is already over the safety line, so it cannot change the recommendation.

## 6. Caveats and hand-off notes

1. `scripts/rebuttal_cases.py` at `e902b8c` does **not** write batch=1 for the 512-token
   cases: `config_for` keeps `native_config`'s 80 GB hint (`batch_size=32`,
   `task_batch_size=32`, `sequence_batch_size=32` for 1.5B; 16 for 3B; 8 for deepseek;
   `scripts/run_iclr2027.py:89-92`) and only forces `(1,1,1)` when
   `max_new_tokens == 4096` (`scripts/rebuttal_cases.py:216-219`). The plans freeze
   `config_sha256`, `implementation_sha256` and `plan_fingerprint`
   (`scripts/rebuttal_cases.py:633-658`), so applying this table requires editing the
   batch hints/template **before** planning, in a fresh run root.
2. The 7B templates (`configs/spectrum_7b/*_4096.yaml`) carry `(16,16,128)`; the runner
   overrides that to `(1,1,1)` for every 4096 case. The recommendation in §4 must be
   injected after that override (or the override must be made profile/table-driven).
3. 80 GB H100 reports 81,559 MiB = 79.65 GiB (torch: 79.18 GiB usable). The historical
   "76.9 GB" danger band is best read as **device memory** (`reserved` in these
   receipts): an allocated=70 GiB point would reserve ~84 GiB here and cannot fit.
   Recommendations therefore target reserved ≈70–72.5 GiB (never above ~73) and report
   the allocated peak alongside. This is the only unit reading consistent with
   both "70 GB target on an 80 GB card" and the 76.9 GB crash.
4. SFT microbatch stays at the case protocol `batch_size=1,
   gradient_accumulation_steps=16` (effective batch 16). The probe's two-step SFT at
   batch 1 records that stage's peak; no SFT microbatch change is proposed because it
   would alter the frozen optimization protocol.
5. Transfer (`transfer.py`) sets all three generation knobs equal to
   `--sequence-batch-size`; decoder/interpolate scripts currently hard-code `(1,1,1)`.
   c16 (HumanEval+) was probed. **c17 (APPS Intro) must not blindly inherit**: APPS
   prompts average 445 tokens and reach 1,324 (HumanEval+ mean 134 / max 391), so its
   KV per sequence is ~1.9× larger at the same S (est. (445+500)/(134+375) ≈ 1.9).
   Scale c17 to S≈640–704 (not 1280) unless a dedicated APPS probe is run.
6. `models/` 7B/deepseek symlink breakage must be fixed before the real runs; probes used
   `hf_cache` snapshots at the exact pinned revisions.
